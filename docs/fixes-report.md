# CHINA AUTO RUS — отчёт по двум исправлениям

Дата: 2026-11-21
Основание: технический аудит (`docs/audit.md`), пункты P0.
Коммит не делался.

---

## Исправление 1. Сохранение отчётов

### Проблемы

1. Имя отчёта строилось с точностью до секунды:
   `report-YYYYmmdd-HHMMSS`. Два сохранения в одну секунду давали один
   и тот же путь, второй отчёт молча затирал первый.
2. JSON и Markdown писались напрямую через `Path.write_text()`. При сбое
   мог остаться частично записанный файл.

### Изменённые файлы

- `src/china_auto_rus/core/report.py`
- `tests/test_report.py`

### Что сделано

**Уникальные имена.** Добавлена `_next_available_stem()`: если пара
`<stem>.json` / `<stem>.md` уже существует, выбирается `<stem>-1`,
`<stem>-2` и так далее. Проверяются оба файла, поэтому недописанная
пара тоже не перезаписывается.

**Защита от одновременных вызовов.** Модульный `threading.Lock`
сериализует выбор имени и запись пары файлов внутри процесса.

**Атомарная запись.** `_atomic_write_text()` пишет во временный файл
`tempfile.mkstemp()` в том же каталоге, делает `flush()` + `os.fsync()`
и затем `os.replace()`. Целевой файл появляется только целиком.

**Очистка при ошибке.** Временный файл удаляется при любом исключении.
Если JSON записался, а Markdown — нет, JSON откатывается, чтобы не
осталось «половины» отчёта.

**Совместимость.** Сигнатура `save_report(report, *, output_dir, stem)`
и формат JSON/Markdown не менялись. Изменилось только поведение при
совпадении имён: добавляется суффикс.

### Тесты

- два сохранения подряд;
- три сохранения с одинаковым `generated_at`;
- повторное сохранение с тем же `stem` не меняет первый файл;
- ошибка `os.replace` — `OSError` пробрасывается, файлов и временных
  файлов не остаётся;
- ошибка записи Markdown — JSON откатывается, каталог пуст.

## Исправление 2. Ограничения на объём сканирования

### Проблемы

Сканер не ограничивал количество файлов, суммарный объём и количество
ошибок. На большом каталоге это давало неограниченный рост памяти
(`files`, `errors`, `seen`, Qt-модели, JSON) и слишком большой отчёт.

### Изменённые файлы

- `src/china_auto_rus/core/models.py`
- `src/china_auto_rus/core/scanner.py`
- `src/china_auto_rus/core/analyzer.py`
- `src/china_auto_rus/core/report.py`
- `tests/test_scanner.py`
- `tests/test_analyzer.py`
- `tests/test_report.py`

### Изменение моделей и формата отчёта — зачем

Без отдельного поля отчёт не может отличить полный анализ каталога от
остановленного по лимиту. Поэтому добавлено необязательное поле
`limit_reached: str | None`:

- в `ScanResult` — со значением `"max_files"`, `"max_total_bytes"`,
  `"max_errors"` или `None`;
- в `AnalysisReport` — переносится из результата скана;
- в JSON — ключ `"limit_reached"`;
- в Markdown — строка «Сканирование остановлено: …» только если лимит
  сработал.

Поле добавлено последним и имеет значение по умолчанию, поэтому
существующее создание моделей и чтение старых полей не ломается.
Формат JSON расширен, а не изменён.

### Реализация

`scan_paths()` и `analyze_paths()` получили параметры:

```python
max_files: int | None = DEFAULT_MAX_FILES
max_total_bytes: int | None = DEFAULT_MAX_TOTAL_BYTES
max_errors: int | None = DEFAULT_MAX_ERRORS
```

`None` отключает соответствующий лимит.

**max_files.** Проверяется перед обработкой очередного уникального
файла: если в результате уже `max_files` записей, обход прекращается.
Файл, который не поместился, не хешируется и не попадает в отчёт.

**max_total_bytes.** Перед хешированием файл статистируется. Если
`total_bytes + size > max_total_bytes`, обход прекращается, а файл не
обрабатывается. Граница включительная: файл, который ровно доводит
сумму до лимита, попадает в результат.

**max_errors.** Ошибки складываются через общий `add_error()`. Хранится
не больше `max_errors`; при достижении лимита скан останавливается.
Лимит действует и на этапе извлечения в `analyze_paths()`: ошибки
разбора архивов/файлов тоже учитываются, анализ прекращается при
достижении лимита.

**Остановка обхода.** `_iter_files()` проверяет общий флаг остановки
(отмена пользователя или достигнутый лимит) на каждом шаге и в начале
обработки каждого каталога. После выхода из цикла выставляется
`ScanResult.limit_reached`.

**Отличие от отмены.** Пользовательская отмена по-прежнему выставляет
`cancelled=True`. Достижение лимита выставляет `limit_reached` и не
маскируется под отмену. В отчёте это отдельная строка.

### Значения по умолчанию

| Лимит | Значение | Почему |
|---|---:|---|
| `max_files` | 100 000 | С запасом покрывает крупный дамп ГУ, но ограничивает список `FileEntry` и Qt-модели. |
| `max_total_bytes` | 16 ГиБ | Типичный дамп прошивки укладывается в объём; хеширование 16 ГиБ занимает десятки секунд. |
| `max_errors` | 1 000 | Достаточно для диагностики, но не превращает отчёт в свалку. |

Все значения — константы в `core/scanner.py`, переопределяются
параметрами вызова. Отдельная система конфигурации не добавлялась.

### Тесты

- превышение `max_files`;
- превышение `max_total_bytes`;
- граница `max_total_bytes` (файл ровно по лимиту включается);
- достижение `max_errors` (на отсутствующих путях);
- достижение `max_errors` на этапе извлечения (битый ZIP);
- отражение лимита в `AnalysisReport`, JSON и Markdown;
- пустой каталог без лимита;
- небольшой каталог без достижения лимитов;
- отмена по-прежнему работает и не путается с лимитом.

## Что не делалось

- Коммит не создавался.
- UI, `scanner`-независимые модули и `docs/audit.md` не изменялись.
- Следующие пункты аудита (отмена внутри SHA-256, ZIP-метаданные,
  кодировки, `%LOCALAPPDATA%` и т. д.) не начинались.
- Межпроцессная гонка имён отчётов теоретически остаётся: защита
  действует внутри одного процесса. Для desktop-приложения этого
  достаточно; при необходимости добавляется резервирование через
  `O_EXCL`.
